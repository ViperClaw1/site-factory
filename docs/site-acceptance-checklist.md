## Как пользоваться

Чеклист один на все сайты. Разделён на два этапа, потому что так устроена работа после совещания 09.11:

- **Этап 1 — сдача.** Сайт собран со всеми общими разделами, языками и настройками, но без товаров.
  Его принимают и выкладывают на сервер. Карточку, корзину и оформление на этом этапе проверяют на
  тестовой позиции каталога.
- **Этап 2 — публикация.** После загрузки каталога: по правилу 06 сайт публикуется, когда на нём
  выложено несколько товаров с описаниями, готовых к продаже. Оплата для этого не нужна: она может
  быть явно выключена, тогда покупка оформляется заявкой (правила 01, 06). Публикация идёт в два
  шага (правило 06, по умолчанию с 10.11). Сначала **закрытый контур**: сайт доступен только команде
  и приглашённым, по паролю или приглашению, закрыт от поисковиков, юридические тексты на сайте не
  публикуются. **Публичный запуск** — открытый доступ, снятие запрета для поисковиков, юридические
  тексты в подвале — после ответа о юрлице и операторе персональных данных (О-3).

Отметки: `[ ]` не сделано · `[x]` сделано · `[б]` заблокировано — общего решения ещё нет; рядом
пишется, какого решения ждём. Заблокированный пункт — не недоработка сайта: его не закрывают
самостоятельно на уровне одного сайта.

Колонка «Чем проверяется»:

- **CI** — проверяется автоматически на каждом PR в `site-factory`. На 09.11 в `.github/workflows` ветки main
  только `ci.yml`: поиск секретов (gitleaks) и lint, type-check, build — только по пакетам,
  затронутым изменением. Развёртывание через GitHub Actions (`pathctl update` на сервере) принято в
  ADR-009 `site-factory` 12.11; на 12.11 в `.github/workflows` по-прежнему только `ci.yml`.
- **Тест** — автоматическая проверка есть в репозитории, но запускается вручную, в CI её нет.
  **Тест (написать)** — такой проверки ещё нет, её нужно написать.
- **Команда** — запускается вручную, результат однозначный.
- **Вручную** — человек открывает сайт и смотрит.

В разделе 1.7 есть колонка «Кто»: **команда** — команда сайта, **развёртывание** — принимающая
сторона, которая ведёт сервер, пайплайн и выкладку; у команды сайта доступа к серверу и пайплайну нет.
«Команда → развёртывание» — делает команда сайта, проверяет развёртывание.

Ссылки на открытые вопросы: «открытый вопрос чеклиста N» — раздел «Открытые вопросы» в конце этого
документа; «О-N» — открытый вопрос правил экосистемы; «вопрос NN» без пометки — номер решения в правилах;
«условия 20.10, вопрос NN» — номер из условий 20.10.

Колонка «Источник» — откуда пункт; список источников и термины — в конце документа. Условия 20.10
(браузеры, поиск, ИИ-ассистенты) предложены 20.10 и снова названы на совещании 09.11, но в правила
экосистемы не внесены. Пункты из них включены в чеклист, пока их не утвердят или не отменят; где у
вопроса 20.10 есть вариант «по умолчанию», указан он.

## Что можно перевести в CI

Сейчас CI ловит секреты и ошибки сборки. Пункты, которые можно проверять автоматически:

- языки, адреса, `hreflang` и `canonical` — тест `locale-suite` уже есть в репозитории, его нужно
  добавить в CI;
- отсутствие прокрутки вбок на 375–1440 px, непереведённых ключей и число кликов пути покупки — тем же
  Playwright;
- текст страницы в ответе без JavaScript и разметка schema.org;
- отсутствие ресурсов Google — поиском по собранным страницам;
- падение при запуске без обязательных переменных окружения (1.7.3) — вместо пустых страниц при
  зелёном CI;
- скорость загрузки (1.4) — Lighthouse CI;
- сборка ZIP площадок из тега и проверка сборки из архива (1.7.13, 1.7.14);
- смоук-проверка после выкладки (1.7.9).

## Согласовано 10.11

Предложено принимающей стороной (развёртывание), разработчик `site-factory` согласился (общий чат, 11:08),
заказчик не возражал (11:14, 11:57).

1. **Как сдаётся сайт.** Тег и GitHub Release; ZIP с исходниками каждого сайта собирает CI из того

   попадает в следующий тег.

   не используется (оставлять ли его для просмотра PR — открыто в ADR-009). Тег →
   проверки → ZIP к Release → подтверждение, что архив получен и проверен (1.7.15) → передача снимка
   кода на сервер и `pathctl update <project>` → сборка образа на сервере → проверка здоровья →
   смоук-проверка → откат при провале. Сервер — в Германии (netcup; ADR-008), Coolify и GHCR в релизном
   пути не участвуют (ADR-009 `site-factory`, принят 12.11; дополнено 12.11).

## Открытые вопросы

1. **Схема тегов.** Один тег на репозиторий со списком затронутых сайтов — проще, но при 20 сайтах
   правка одного даёт новый номер всем; или тег на сайт. Поправки, ревизия 3 (раздел 9), — тег на
   площадку `<app>/vX.Y.Z`, тег репозитория не используется. ADR-009 `site-factory` принят 12.11, но
   о тегах говорит по-разному: в разделе «Status» — решено, тег на сайт `<app>/vX.Y.Z` (по поправкам,
   раздел 9); в разделе «Release» — один тег `vX.Y.Z` с пометкой «to confirm» и переход на
   `site01/vX.Y.Z` при необходимости; в «Consequences» схема тегов названа открытой. Нужно одно решение
   и одна запись в ADR-009.
2. **Закрыт 12.11. Coolify или выкладка по SSH.** Выкладка — из GitHub Actions по SSH в
   `pathctl update` на сервере; Coolify в релизном пути не участвует (ADR-009 `site-factory`, принят
   12.11; поправки, ревизия 3, раздел 2).
3. **Замещающий для развёртывания.** Сервер, выкладку, резервные копии и откат ведёт один человек —
   это узкое место (пункт 1.7.12). Дополнено 12.11: по поправкам, ревизия 3 (раздел 5.1), замещающий —
   технический лид заказчика, права только на время сбоя; пока кандидатура не подтверждена, риск
   записывается в итог приёмки. По ADR-009 `site-factory` замещающий обязателен и получает те же права
   и инструкцию. Нужно: кандидатура (подтверждает заказчик) и одно правило о правах.
4. **Кто подтверждает выкладку** после получения архива (1.7.15). Дополнено 12.11: по ADR-009
   `site-factory` выкладку запускает заказчик или владелец инфраструктуры, получение архива подтверждает
   заказчик, запись — в `report.md`. Остаётся: когда выкладку запускает владелец инфраструктуры,
   пайплайн не ждёт заказчика, и подтверждение остаётся записью в отчёте.
5. **Формат чеклиста.** Предложено вести его машиночитаемым файлом (`checklist.yaml`: этап, категория,
   важность, автоматический или ручной, команда, ожидаемый результат, источник) и собирать из него
   страницу и отчёт по релизу; автоматические пункты отмечает CI. В ADR-009 `site-factory` этот вопрос
   тоже открыт.
6. **Перечень требований к карточке товара.** По умолчанию — схема стандарта каталога; на
   совещании 09.11 решено свести перечень заново (пункт 1.6).
7. **Профили стран.** В справочнике `Path-platform-standards` есть профили Германии, Эстонии, ЕС,
   России и США (черновики, юристом не проверены). Нет профилей рынков запуска ADR-013 (Великобритания,
   Канада, Австралия, Новая Зеландия); по ADR-013 они нужны до юридических текстов и публичного запуска
   (пункты 1.7.20 и 2.2). Япония и Китай по правилу 01 — позже (по умолчанию, 12.11).
8. **Китай — рынок продаж.** Отложен: по правилу 01 Япония и Китай — позже (по умолчанию, 12.11), в
   условиях 20.10 по умолчанию стоит «пока только язык». Когда дойдёт до продаж, в чеклист добавляются
   размещение в Китае или Гонконге, местные способы оплаты и входа, Baidu и требования PIPL.
9. **Условия 20.10** (браузеры, поиск, ИИ-ассистенты) в правила экосистемы не внесены. Утвердить их
   или поправить.
10. **Cookie и трекинг.** Правило 05 — трекинг включается только после согласия, везде; ADR-008
   `site-factory` приведён к нему поправкой 10.11 (прежде — в США до отказа). Отказ вместо согласия в США —
   открытый вопрос правил О-10 (пункт 1.6).
11. **Закрыт 12.11. Номера ADR.** Пакет ADR 12.11 называл свои решения ADR-009–012, а в `site-factory`
   номера 009–011 были заняты. На `938e04d` пакет записан под номерами `site-factory`: развёртывание —
   ADR-009, аналитика — ADR-005, данные и файлы — поправки к ADR-002 и ADR-008, справочники и
   юридические тексты — ADR-012, рынки запуска — ADR-013.
12. **Закрыт 12.11. Чем запускается выкладка.** Тег запускает проверки и ZIP к Release; выкладку
   запускает вручную человек из разрешённого списка после подтверждения получения архива (ADR-009 `site-factory`, принят 12.11; пункты 1.7.8, 1.7.13–1.7.15). Выкладка по пушу
   в `main` из пакета ADR 12.11 в принятый ADR-009 не вошла.
13. **Контракт `/api/health`.** ADR-009 `site-factory` (принят 12.11): `{"status":"ok","version":"<sha>"}`,
   проверка неглубокая — без Directus и Supabase, чтобы сбой CMS не останавливал рабочий контейнер.
   Поправки, ревизия 3 (1.7.5): ещё коммит и проверка базы, 503 при недоступной базе. Нужно: оставить
   один адрес по ADR-009 или добавить второй — с проверкой базы для проверки после выкладки.
14. **Пять вопросов пакета ADR 12.11.** На `938e04d` `site-factory`: бакет R2 — исключён (ADR-008,
   поправка 12.11); аналитика — только своя или никакой, облачная не используется (ADR-005, 12.11;
   инструмент — Umami, предложен); юрисдикции запуска — США, Великобритания, Канада, Австралия, Новая
   Зеландия (ADR-013, предложен); поля таблиц справочников и роли Directus — ADR-012 (предложен).
   Остаётся: утвердить ADR-012 и ADR-013 и назвать, кто из команды получает доступ в Directus и с какой
   ролью (пункты 1.7.16, 1.7.18–1.7.20).
15. **Россия.** Ответ заказчика 12.11 21:15: Россия и СНГ — один из рынков, хранение данных
   покупателей из России в России — «лучше заложи». В правилах 12.11 (правило 01, О-1 закрыт): хранение
   в России закладывается с начала (ст. 18 152-ФЗ — вывод правил, а не слова заказчика), как — решают
   исполнители. В `site-factory` на `938e04d`: ADR-012 (предложен) называет продажи в России поводом для
   регионального контура — той же схемы в стране, со своими покупателями и заказами, — и считает, что
   сегодня этот повод не наступил; ADR-013 оставляет Россию открытой со ссылкой на О-1. Нужно: решение
   исполнителей, как и когда закладывается хранение данных покупателей из России.

**Термины**

- **CRM** — система, куда попадают заказы и заявки покупателей.
- **`hreflang`, `canonical`** — разметка в коде страницы: связывает языковые версии одной страницы и
  указывает поисковику основной адрес.
- **`locale-suite`** — набор автоматических проверок языковых адресов в репозитории `site-factory`,
  написан на Playwright (инструмент, который открывает сайт в настоящем браузере и проверяет его).
- **IndexNow** — способ сразу сообщить поисковикам о новых и изменённых страницах.
- **`not_sold_to`** — поле карточки в стандарте каталога: страны, куда товар не продаётся.
- **ADR-008** — записанное решение об общей базе продаж и едином входе.
- **Тег, Release** — метка версии в git и страница версии на GitHub, к которой прикладываются файлы.
- **GHCR** — реестр образов контейнеров GitHub. В релизном пути не используется (ADR-009 `site-factory`,
  принят 12.11): образ собирается на сервере и помечается полным SHA коммита.
- **Смоук-проверка** — короткая проверка сразу после выкладки: сайт отвечает, адреса и сертификат в
  порядке, ошибок нет.
- **lockfile** — файл с точными версиями зависимостей (`pnpm-lock.yaml`); сборка по нему повторяема.
- **`turbo prune`** — команда, которая выделяет из общего репозитория один сайт с нужными ему общими
  пакетами.
- **`workflow_dispatch`, environment `production`** — ручной запуск задания GitHub Actions и окружение,
  выкладка в которое ждёт подтверждения человека (на бесплатном тарифе для закрытых репозиториев
  недоступно).
- **SHA** — уникальный номер коммита в git.
- **gitleaks** — поиск секретов в коде и истории репозитория.
- **TLS, HSTS** — шифрование соединения и заголовок, который велит браузеру всегда ходить на сайт по
  https.
- **CSP, CSRF** — заголовок, ограничивающий, откуда страница загружает скрипты, и защита форм от
  отправки с чужих сайтов.
- **Lighthouse** — инструмент Google для замера скорости и качества страницы.
- **Coolify, Traefik, SSH** — панель развёртывания контейнеров, прокси перед ними и прямой доступ к
  серверу. Coolify в релизном пути не участвует (открытый вопрос чеклиста 2): ADR-009 `site-factory`
  заменяет прежнее решение о Coolify, ADR-003.
- **`pathctl`** — команда на сервере: принимает снимок кода, собирает образ, проверяет здоровье и
  откатывает при провале; ключ выкладки из GitHub Actions разрешает только её.
- **Directus, MinIO** — интерфейс редактирования содержимого поверх общей базы; собственное хранилище
  файлов с интерфейсом S3.
- **Supabase** — база данных и связанные с ней сервисы, на которых по ADR-008 строится общая база.
- **LCP, CLS, INP** — показатели скорости и стабильности страницы: время до появления главного
  содержимого, сдвиг вёрстки при загрузке, задержка отклика на действие.
